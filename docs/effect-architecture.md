# Server/data architecture

React stays plain React. Server components use `ListingRepo`; ingestion runs in authenticated server route handlers. Keep supabase-js, runtime creation and credentials in server-only modules. Use Effect 4’s installed `Context.Service`, `Schema`, `Effect.fn`, `Layer` and `ManagedRuntime` APIs. The sample repository remains an explicit demo mode; database errors must not silently select it.

## Boundaries

Use a public-key Supabase client for directory reads and a separate service-role client for ingestion, with session persistence/refresh disabled. Never render public results with the privileged client. A Supabase service owns the client; wrap thenable queries with `Effect.tryPromise`, inspect the returned `error`, and map failures to typed database errors. Maintain separate read and ingestion runtimes.

The Supabase-backed `ListingRepo` selects active listings and noncancelled occurrences, joins current matching evidence/source names, projects into the UI model and decodes at the boundary. Unknown values remain null in the existing nullable UI model; each projected session has a unique `sessionId` alongside the shared listing `id`. Apply New York local date boundaries as instant ranges, including DST. Use the generated search document for full-text search, SQL filters and coordinate bounding boxes; the existing indexes do not promise distance ordering.

Ingestion is fetch → source Schema decode → normalize → dedupe → RPC → finish run. Source adapters validate identity, NYC location, dates, eligibility and applicable explicit cost text. Keywords only find candidates. Normalize HTML to safe text, validate URLs/coordinates and preserve unknown values. Send `status: "active"` explicitly when suitable for publication; omitted status becomes hidden. No review/approval workflow runs here. Classify parse/normalize/fetch/database errors, sanitize logs and count rejected candidates.

## Transaction contract

The initial migration defines `public.ingest_listing(p_listing jsonb, p_occurrences jsonb, p_evidence jsonb) returns uuid`. Call with `client.rpc("ingest_listing", { p_listing, p_occurrences, p_evidence })`. This is implemented SQL; the Effect adapter and route remain to build.

- `p_listing` is a **full normalized snapshot**, using SQL column names. Required: `source_id`, `dedupe_key`, `title`, `category_slug`, `source_url`. Other writable listing fields are optional; omissions reset them to null/defaults (`status` hidden, `cost_status` unverified, `discovered_by` deterministic). Identity, first/last-seen and verification timestamps are database-controlled. Upsert identity is `(source_id, dedupe_key)`; `first_seen_at` is preserved and `last_seen_at` refreshed.
- `p_occurrences` is an array (use `[]` for none) of `starts_at`, optional `ends_at`, `source_occurrence_key` and `cancelled`. Upsert by stable source key when supplied, otherwise by `(listing_id, starts_at)`. Keyed rescheduling preserves the occurrence ID. An unkeyed update at the same instant preserves any existing source key; different non-null keys at one instant are rejected rather than overwriting identity. Omitted occurrences remain; cancellation must be explicit. A keyed reschedule onto another occurrence’s start time fails atomically.
- `p_evidence` is an array of `quote`, `url`, `captured_at`, `method`, `supports_cost_status`, and optional `source_id` (defaults to the listing source). Parent IDs are supplied by the function. Evidence identity is `(listing_id, url, captured_at, supports_cost_status)`: exact repeats are skipped; changed content under that identity is rejected. Only newly inserted evidence matching the current cost claim can advance `last_verified_at`, to the maximum capture time without moving it backwards. Reusing historical evidence does not create a new check.

The function is `SECURITY INVOKER`, with an explicit search path and execute granted only to `service_role` (besides the database owner). It relies on that role’s DML grants and RLS bypass, without owner elevation. Each RPC is one transaction. Deferred constraint triggers require matching evidence and verification for both free statuses at commit; a free listing and its evidence can arrive in either order. Missing evidence aborts the transaction, including listing/occurrence changes. Do not split these writes across HTTP calls or use `Promise.all` as a transaction substitute.

The schema intentionally has no manual parent locking. Concurrent direct evidence removals/claim changes are not covered by the single-session checks; serialize ingestion operationally per source, and keep evidence append-only in adapters. Table grants exclude TRUNCATE. Quote accuracy and capture timestamps remain trusted adapter inputs.

Use plain service-role inserts/updates for `ingestion_runs`: insert a running record before work, then update status, `finished_at`, counts and sanitized error on completion or typed failure. The unique running-run index rejects overlapping runs for a source. A hard timeout may leave a running row; inspect and explicitly fail it before restarting. Partial/failed runs never reconcile missing occurrences. Reconcile only complete successful snapshots of the same source window.

## Cron and deferred work

A future `GET(request: Request): Promise<Response>` route verifies the configured cron bearer secret before creating the privileged client or fetching sources. Run ingestion through the managed runtime, return counts on success and sanitized non-2xx errors on failure. Use cancellation/time limits, bounded transient retries and short per-source runs. Deployment cadence and execution limits must be checked before scheduling.

Deferred: review workflow, freshness/stale marking, AI discovery and admin UI.

## Validation

Committed tests in `supabase/tests/migrations.test.ts` run under `pnpm test` (Vitest) using one in-memory PGlite database with the contrib `pg_trgm` extension. They simulate `anon`, `authenticated` and a RLS-bypassing `service_role`, apply broad Supabase-style default grants **before** the migration, then apply `20261111000000_init.sql`. Tests cover deferred evidence and verification for both free statuses, either insertion order, deletion/claim-change/parent-move protection and cascading deletion; RPC idempotency, timestamps, keyed/unkeyed identity, rescheduling, collisions, cancellation, omitted sessions, malformed payloads and atomic rollback; search and taxonomy renames; RLS, function execution and table grants including denied TRUNCATE. These are repeatable embedded PostgreSQL checks, not PostgREST, hosted Supabase or concurrent-session integration tests. Run local Supabase integration checks before deployment. Quote relevance and actual capture times remain adapter responsibilities.

## URL and search parity

`src/lib/listings/url.ts` (`HttpUrl`, backed by the WHATWG `URL` parser) is the application source of truth for URL parsing, including valid URL structure and rejection of credentials and non-HTTP(S) schemes. The immutable SQL `public.is_http_url(text)` helper guards all four URL columns with a deliberately conservative subset: lowercase `http://` or `https://`, dotted ASCII DNS labels, alphabetic final label, no localhost suffix, optional numeric port up to 65535, no whitespace or backslashes, and no userinfo in the authority. Null registration URLs remain allowed. This is not a complete WHATWG parser, DNS resolution or an SSRF/public-IP filter; revalidate using `HttpUrl` at application boundaries.

The shared corpus in the committed test imports `HttpUrl` directly and asserts SQL and TypeScript outcomes for every case, then exercises all four SQL column constraints. Both accept HTTPS/HTTP DNS URLs, query/fragment URLs, subdomains and numeric ports, `@` in paths/queries and percent-encoded spaces. Both reject user/password, username-only and percent-encoded username credentials; missing hosts (`https://`, `https://?`, `https://#`, `https://?example.org`); JavaScript/data/FTP schemes; protocol-relative URLs; junk/empty strings; whitespace in hosts; and invalid or overflowing ports. Intentional stricter SQL rejections (accepted by WHATWG) are leading-hyphen host labels, localhost and subdomains, single-label hosts, IPv4/IPv6 literals, raw Unicode hosts, uppercase schemes, surrounding whitespace, spaces in paths and backslash separators. SQL has no intentional looser cases; this finite corpus cannot prove complete parser equivalence.

`search_document` is a trigger-maintained tsvector, not a generated column, with a GIN index on it and a trigram index on the title. This avoids denormalized taxonomy name columns while correctly joining current category and discipline names. Every listing insert/update recomputes title, description, venue, neighborhood, borough, discipline name and category name; taxonomy name updates refresh affected listings. The regression includes “Harlem” absent from title/description. Full-text stemming/tokenization still differs from the sample repository's substring search; address-independent facets remain deferred.
